# 项目结构说明书（architecture）

> 给"第一次做项目"的人看：每个文件夹是干什么的、为什么这样分、我的新代码该放哪里。
> 这份文档本身也是一个面试素材——面试官很爱问"你的项目结构为什么这么分"。

---

## 一、一句话理解

这个项目分成 **三层 + 三个配套**：

```
内容(data)  →  逻辑(src/core)  →  表现(scenes + src/ui，M4 才出现)
                    ↑
                测试(tests) 直接测逻辑，不经过表现
```

配套：**文档(docs)** 解释设计、**工程基建**(project.godot / .gitignore / .github) 让项目能跑能验、
**README + devlog** 让项目可被理解和维护。

---

## 二、目录逐个说明

```
reaction-card-battler/
├── project.godot            ← 引擎入口配置
├── README.md                ← 项目说明书（给人看"这是什么、怎么跑"）
├── devlog.md                ← 开发日志（给自己看"我上周在干嘛"）
├── .gitignore               ← 哪些文件不进 Git
├── 项目计划_知识储备与行动大纲.md  ← 40 周计划（不在代码里，但很重要）
│
├── data/                    ← 【内容层】数据，不是代码
│   ├── tables/              ← 实际数据（游戏运行时读这里）
│   │   ├── elements.json
│   │   ├── reactions.json
│   │   ├── cards.json
│   │   └── enemies.json
│   └── schema/              ← 字段规范（数据契约，不参与运行）
│       └── README.md
│
├── tools/                   ← 【工具链】校验器、平衡模拟器（M2-M3 出现）
│   └── README.md
│
├── src/
│   └── core/                ← 【逻辑层】规则与计算，绝不碰界面
│       ├── element.gd
│       ├── damage.gd        ← 纯函数：伤害与反应（M1/M2 共用）
│       ├── card.gd
│       ├── buff.gd
│       ├── unit.gd
│       ├── reaction_table.gd
│       ├── data_loader.gd
│       └── battle.gd
│
├── tests/                   ← 【测试层】用代码验证规则对不对
│   ├── data_test.gd         # 数据链路（JSON / 元素工具 / 反应表）
│   ├── unit_test.gd         # 单位数值（护盾 / 治疗 / buff 生命周期）
│   ├── damage_test.gd       # 伤害算法（纯函数）
│   ├── battle_test.gd       # 战斗流程（回合交换 / 能量 / 附着 / 胜负）
│   └── run_battle.gd        # 不是测试：手动跑一局看日志
│
├── docs/                    ← 设计文档
│   ├── architecture.md      ← 本文件
│   ├── from-genshin-install.md ← 从原神发行包观察到的结构（哪些能抄）
│   ├── element-reactions.md
│   └── adr/001-data-driven.md
│
└── .github/workflows/ci.yml ← 云端自动跑测试
```

### `project.godot` —— 引擎入口

Godot 用这个文件识别"这是一个项目"，里面写着项目名、主场景、渲染方式。
**类比**：Java 的 `pom.xml`、Node 的 `package.json`。你一般不动它，除非要改窗口大小、加插件。

### `README.md` —— 项目说明书

标准内容：这是什么 / 怎么跑起来 / 目录结构 / 当前状态 / 路线图。
**判断标准**：一个陌生人拿到仓库，只看 README 就能跑起来，说明它合格。

### `devlog.md` —— 开发日志

每周 3 行：做了什么 / 卡在哪 / 下周做什么。
**为什么必须有**：三个月后你会忘记"当初为什么不用另一种写法"，答案就在这。

### `.gitignore` —— 什么不进版本库

`.godot/`（编辑器缓存，几百 MB，每次自动生成）、`build/`（导出产物）不该进 Git。
**判断标准**：能自动生成的东西，一律不进版本库。

### `data/` —— 【内容层】数据

卡牌、敌人、元素反应全部是 JSON。**改数值不用改代码，改完重启就生效。**

为什么单独放一层：
- 策划改数值不该碰代码（真实项目里这两个是不同岗位）
- 数值调整要能快速试错（改 JSON → 重启 → 看结果）
- 数据可以批量生成、可以被工具处理

### `src/core/` —— 【逻辑层】规则

项目的"大脑"。回合怎么走、伤害怎么算、反应怎么触发，全在这。
**它有一个铁律：不知道界面的存在。**
里面不许出现 `get_node()`、不许出现按钮、不许出现颜色。只有纯逻辑。

**为什么这条铁律值钱**：因为这样它才能被测试（不需要开窗口），也才能被复用（以后换网页版、命令行版，逻辑直接搬走）。

### `tests/` —— 【测试层】规格

`battle_smoke_test.gd` 的 24 项断言，本质是**用代码写的需求文档**：
"火打水附着应该打出 1.5 倍伤害"——这句话在测试里是一行可执行的断言。

`run_battle.gd` 不是测试，是**手动跑一局看日志**的工具，用来调规则。

**为什么测试要单独放**：测试和生产代码分开，发布时可以不打包进去；也提醒你"测试是项目的一部分，不是附属品"。

**为什么测试按"被测单元"拆成 4 个文件，而不是每个功能一个文件**：
一个文件对应一个"被测试的对象"（数据链路 / 单位数值 / 伤害算法 / 战斗流程），
这样你写哪个文件，就跑哪个测试文件，失败信息也不会混在一起。
如果按功能点拆（"回合交换测试""附着测试""能量测试"…），会出现 20 个文件、每个都 copy 一遍断言函数。

### `docs/` —— 设计文档

- `element-reactions.md`：元素反应表、附着规则、手算验证（**先写它，再写代码**）
- `adr/001-data-driven.md`：架构决策记录（ADR）——记录"为什么这么选、代价是什么"

**ADR 为什么值钱**：面试官问"你为什么用数据驱动"，你拿出一份写清楚的决策文档，和说"我觉得这样比较好"，是两个段位。

### `.github/workflows/ci.yml` —— 持续集成

每次 push，GitHub 会开一台干净机器：装 Godot → 导入项目 → 跑测试。
**测试红了，就是你的代码有问题**（不是"我电脑上能跑"）。

## 三、依赖方向（最重要的规矩）

```
        ┌────────────────┐
        │  UI / scenes   │  M4 才有：显示、输入、动画
        └───────┬────────┘
                │ 只能单向向下调用
        ┌───────▼────────┐
        │   src/core/    │  规则：不许 import UI
        └───────┬────────┘
                │ 只能单向向下读取
        ┌───────▼────────┐
        │     data/      │  内容：JSON
        └────────────────┘

        tests/ ──直接测──▶ src/core/（绕过 UI）
```

**三条禁令**：
1. `core` 里不许出现界面相关代码
2. `core` 里不许硬编码卡牌/敌人/数值（必须读 `data/`）
3. UI 不许直接改数据文件，只能通过 `core` 提供的方法

违反了会怎样？项目不会立刻坏，但会变成"改一个数值要翻三个文件""想加个测试发现要先开窗口"——**这就是烂代码的全部来源**。

## 四、我的新代码该放哪？（决策树）

```
我要写的东西是……
├─ 数值 / 卡牌 / 文案 / 配置？        → data/*.json
├─ 规则 / 计算 / 流程？               → src/core/
├─ 按钮 / 动画 / 显示？               → src/ui/、scenes/（M4 才建）
├─ 验证规则对不对？                   → tests/
├─ 解释"为什么这么设计"？             → docs/adr/
├─ 这周做了什么？                     → devlog.md
└─ 教别人怎么用？                     → README.md
```

再问一句：**这个文件只做一件事吗？**
`battle.gd` 只负责战斗，不负责存档；以后存档要单独 `save_system.gd`。
一个文件超过 300 行，通常说明它干了太多事。

## 六、一句话记住

**文件夹不是分类，是"依赖关系 + 谁负责改"的边界。**
分层的目的不是好看，是让"改数值的人"和"改规则的人"互不干扰，让你的代码能被测试、被替换、被维护。
