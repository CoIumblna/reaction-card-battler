## 2. 角色与纪律（重要）

- **学员写 `src/core/*.gd` 实现；agent 只做**：code review、答疑、出题、解释 API、跑测试验收、指设计问题。
- agent 默认负责：`docs/`、`tests/`、`data/`、`tools/`、CI、git 提交与推送。
- **不许为了变绿改测试/数据**；改测试必须同步文件末尾 `EXPECTED_CHECKS`。
- `tests/pending/` 不进 CI、不进主套判定；**全绿后 `git mv` 到 `tests/` 才启用**。
- 提交前必须全绿（`run_tests.bat` 退出码 0 + 无 `[FAIL]` + 无 `SCRIPT ERROR`）；CI 还会跑 `tools/validate_data.gd`。
- **`run_tests.bat` 是唯一的验收入口**，分三段：
  - **PART 1 主套**（`tests\*_test.gd`，四重判定）
  - **PART 1.5 待启用基线**（`tests\pending\*_test.gd`）：每个文件打一行 `[READY  ] name  N checks --> git mv ...`
    或 `[PENDING] name  N checks / M failed`，**只报告、永不判失败**。跟主套结果同一个终端，不用去别处翻
  - **PART 2 详细自检**（`tools/preflight.ps1`，7 项）：数据校验 / `has_acted` 残留 / `EXPECTED_CHECKS` /
    兵科覆盖 / **平衡冒烟 100 场** / 脚本编码 / 工作区噪音
  三段都过才打印 `===== ALL GREEN =====`；只想跑详细自检用 `tools\preflight.bat`。
  脚本化调用（CI、agent）加 `set NO_PAUSE=1`，结尾就不会停在 `pause` 等按键。
- 提交信息用「类型(范围): 中文摘要」，多行用 `git commit -F <文件>`，文件用 **UTF-8 无 BOM**；写 `.bat` 要 CRLF + 纯 ASCII。
- 测试脚本的 Godot 路径是**相对仓库**解析（`run_tests.bat` / `check.ps1`，可用环境变量 `GODOT` 覆盖），不要改回绝对路径。
- **每个任务开工前先报预计用时**（学员和教练都要）：格式 `预计 X–Y h（依据：§NN 任务卡难度 ★★★ + 预计行数 N）`。
  出处是 `docs/implementation-tasks.md` 进度总览表里的「预计用时」列；做完后回头对一下实际用时，
  偏差超过 2 倍就在复盘里记一句原因（估错的往往是没算"卡在某个 GDScript 语义上"的时间）。
  **2026-11-25 实测校准**：学员当天做完 M3.1 收尾 + M3.2 + M3.3 三块，**实际编码合计只有 3–4 h**，
  其余时间全在等 agent 反馈（写→跑测试→贴报错→等 review→再改）。所以表里的区间现在读作「乐观上限」，
  未完成的块已按下修后的倍率改过；真正决定日历进度的是**返工轮数**，不是打字速度。

### 2.1 工作方式约定（2026-11-25 起，接手的 agent 也要遵守）

学员对 agent 的工作方式有明确要求，四条：

1. **同一轮内并行发工具调用**：读多个互不相关的文件、搜多个关键词、查多个接口时，一次性全发出去，
   **禁止逐个串行**。验收跑测（主套 + 数据校验 + 平衡冒烟 + 独立 worktree 复验）也是同一批发出。
2. **`subagent` 收结论，不收过程**：探索性、可隔离的工作（调研、审查、独立实现一份参考实现）
   下发给子 agent，主上下文只回收结论与文件路径，不把原始过程（大段日志、逐行 diff）带回来。
   - 隔离靠 **独立的 `git worktree`**：给每个子 agent 分一个互不重叠的目录（如 `_ref_m35` / `_ref_m37`），
     各自只改自己那份，主工作区不动。
   - **把子 agent 当「coding 工具」而不是「同事」**（2026-11-25 校准）：不要让它自己读一堆文档去理解项目，
     那既慢又费 token。正确做法是**主 agent 先把规格啃完**，然后给它**函数级指令**：
     写哪个文件、加什么函数签名、插在第几行附近、边界条件是什么。子 agent 只负责敲代码，
     **正确性由主 agent 事后核验**（复核 diff + 独立跑测试 + 故意改坏看测试是否变红）。
   - **按难度调思考强度**：小块/机械改动（加个加载函数、补个谓词）可以把子 agent 的
     `reasoning_effort` 调低甚至关掉，模型本身也选小的；只有需要自己摸清调用链的活才给高思考。
3. **`workflow` 做同构批量**：存在几十个同构子任务时（批量扫描全仓、批量迁移、多角度分析），
   写成编排脚本一次性并行分发，不要一个个 `subagent` 排队。
4. **长命令走后台 job**：构建、全量测试、平衡模拟、push 重试等长命令用后台跑（`run_in_background`），
   不要阻塞等待；先去推进其他工作，需要结果时再统一收割（`job_output`）。
5. **给学员「思路」，不给「成品代码」**（2026-11-26 校准，学员原话：「以后请提供给我思路而不是
   直接贴给我一段代码」）。作业单写到这个粒度就够：规则是什么、三个对象各自手上有什么、
   有哪几条路可选、各自的代价、判据是什么、坑在哪。**函数体让学员自己写。**
   - 例外：**签名**可以给（`stat_mod(stat: String, table: StatusTable) -> int`），因为签名是接口约定；
     但循环体、条件判断这些实现细节不要给。
   - 必须解释**为什么**这么选（例如「认 `b.kind` 但不硬编码数值，否则改 JSON 不跟随」），
     而不是只给对的写法 —— 只给答案等于替学员做题。
   - 与第 2 条的区别：第 2 条说的「函数级指令」是给**子 agent（coding 工具）**的；
     第 5 条是给**学员（人，在学 GDScript）**的。对象不同，粒度也不同，别混。

**一条实测校准**：本机 `node` 不存在，所以 `create_worktree` 工具必失败，隔离树一律用
`git worktree add --detach <路径> <commit>`，用完 `git worktree remove --force <路径>`。

### 8.1.1 本轮踩到的两个「看起来对、实际反了」的坑（下次容易再犯）

**① `_mulligan_of()` 的语义是「已用过」，不是「还能用」**
```gdscript
func _mulligan_of(owner:String) -> bool:
	return mulligan_used if owner == "player" else enemy_mulligan_used
```
守卫写成 `if _mulligan_of(owner) == false: return false` 会**恒成立**（开局时标记就是 false），
于是 mulligan 一次都执行不了。正确写法是 `if _mulligan_of(owner): return false`。
**教训**：把复合守卫拆成三条独立 `if`，别挤在一个 `||` 链里 —— 挤一起时方向反了很难看出来。

**② Nil 判空的方向写反**
```gdscript
if board.find_first_unit("front"): break   # ❌ 有目标反而退出
if tgu == null: break                      # ✅ 没目标才退出
```
写反后 `battle_m2_test` 的「敌方支援线单位打不到 HQ，就打我方前线单位」会红
（期望 HQ/单位受伤，实际一点没打）。**教训**：判空的条件要跟着"没有目标"写，而不是跟着变量名想当然。

**③ GDScript 参数是值传递，写 `swap(a,b)` 无效**
```gdscript
func swap(a, b) -> void:
	var tmp = a
	a = b
	b = tmp
```
调用 `swap(dck[i], dck[j])` 只交换局部副本，`dck` 完全不变 —— 洗牌变成空操作，
而且**测试可能测不出来**（`_draw_into` 从牌库头部取牌，换回尾部的牌即使不洗也会换出手牌）。
**教训**：数组元素交换必须在持有数组的上下文里直接下标赋值。

**D5 正确形状**（`_begin_turn()` 必须在 `if` 外，两条分支都走）：
```gdscript
func begin_first_turn() -> void:
	opening_phase = false
	if first_move == "enemy":
		_enemy_turn()
	_begin_turn()
```

**D6 正确形状**：`mulligan()` 守卫顺序 = `not opening_phase` → `cards.is_empty()` →
`owner=="player" and mulligan_used` / `owner=="enemy" and enemy_mulligan_used` → 每张都在自己手牌里
（否则 false）；然后 erase → 追加回该 owner 的牌库 → 置 used 标记 → `_shuffle_rng()` → `_draw_into(owner, cards.size())`。
`_shuffle_rng` 必须自己写 Fisher-Yates（`RandomNumberGenerator` 没有 `shuffle`，`Array.shuffle` 不可复现）：
```gdscript
func _shuffle_rng(arr: Array) -> void:
	for i in range(arr.size() - 1, 0, -1):
		var j: int = rng.randi_range(0, i)
		# swap arr[i] / arr[j]
```

### 14.2 本轮修掉的 3 处**测试**缺陷（教练的活，学员不用管）

> 这三条都是「测试自己写错了」，会让**错误实现也变绿**，或者让**正确实现永远红**。

**① `deck_build_test.gd` [3]：独立性断言恒真**
```gdscript
_check(p != e or p.size() == e.size(), "两次加载互不影响（不是同一个数组引用）")  # ❌
_check(not is_same(p, e), "两次加载不是同一个数组引用")                          # ✅
_check(not is_same(p[0], e[0]), "展开后的 Card 对象也不共享引用")                # ✅ 新增
```
`or` 后半句在正常实现下**永远为真**（双方都是 39 张），整条断言无论前半句真假都通过。
实测：故意写一个「返回同一个共享数组」的错误实现，旧断言照绿，新断言立刻红。
注意 GDScript 里 `Array` 的 `==` 是**内容比较**（`[1,2,3] == [1,2,3]` 为 true），判引用同一性必须 `is_same()`。

**② `deck_build_test.gd` [4]：「总数不对」用例从没测到总数分支**
原来写 `[{ "id": "footman", "count": 10 }]`，它**同时**违反同名上限（4），而实现里同名检查在总数检查**之前**
→ `push_error` 打的是「同名卡 footman 超过上限 4（10 张）」，**总数校验从未执行**（日志已实证）。
改成 37 张、每个 id 合法、同名都不超 4 的牌组，日志确认命中 `牌组张数必须 = 39（实际 37）`。
`EXPECTED_CHECKS` 10 → **11**。

**③ `stat_mod_test.gd` [5][6]：`b.end_turn()` 会真的跑敌方 AI**
```gdscript
var tgt := _target(b)      # 放 enemy_support
b.end_turn()               # ← 敌方 AI 真的跑一遍，把靶子挪到 front 0 号格
var atk := _atk(b)         # 放 front 1
b.attack_unit(atk, tgt)    # ← 两者同线，跨度 0 → 直接返回 false
_check_eq(tgt.hp, 7)       # ← 血量没变，红
```
**这条测得不是「buff 失效」，而是「攻击被拒」**。参考实现怎么改都过不了，因为根本不是实现问题。
修法：靶子直接放 `front`（AI 不会再挪它）、攻击者放 `player_support`（与 front 相邻，跨度 1），
并**补一条 `_check(b.attack_unit(atk, tgt), "buff 失效后攻击成立（防空跑）")`**。
`EXPECTED_CHECKS` 6 → **7**。

`deck_build_test` 开 M3.5 前重跑五条反假绿探针，**探针 ② 暴露了测试漏洞**（实现照绿）：

| 探针 | 结果 |
|---|---|
| ① `total != DECK_SIZE` → `total > DECK_SIZE` | ✅ 红「总张数不是 39（期望 0，实际 37）」 |
| ② `MAX_SAME_CARD := 4` → `5` | ❌ **仍 11/11 全绿 = 假绿** |
| ③ 所有 Card 共享同一对象 | ✅ 红 2 项（`footman 期望 4 实际 39`、`guard 期望 3 实际 0`） |
| ④ 非法时仍继续展开 | ✅ 红「总张数不是 39（期望 0，实际 37）」 |
| ⑤ `if count <= 0:` → `count < -100:` | ✅ 红「count <= 0 → 空数组（期望 0，实际 39）」 |

**根因**：`bad_dup` 原写 `[{footman,5},{archer,34}]` —— footman 超名字上限、**archer 34 也超**，
两条同时违规；放宽 footman 上限后 archer 仍然触发拦截，断言照样通过 ⇒ **从没测到「同名上限」这一条**。
`bad_count` 原写 `[{footman,0}]` 同病：count 0 让总数变 0，同时违反「总数必须 39」。

**修法（三个非法用例全部重写成「只违反一条规则」，项数仍是 11）**：
- `bad_total`：37 张、每 id 合法、同名都不超 4（保持原样）。
- `bad_count`：`footman 0` + 其余 9 种各 4 + `fire_burst 3` = **39 张**，只违反 `count > 0`。
- `bad_dup`：`footman 5` + 其余 8 种各 4 + `guard 4` + `mend 2` = **39 张**，只违反同名上限。

**通用教训（比这三条用例更重要）**：**每个非法用例必须「只违反一条规则」**。
否则你把那条检查从实现里删掉，测试都不会红 —— 测的不是你以为的那条。
验证手段只有一条，和 §14.3 一样：**故意把实现改坏，看测试会不会红**；绿了就说明用例有重叠。

### 16.4 `.tscn` 手写最小结构（M4 全阶段沿用的约定）

### 16.6 行级手术：为什么不能整份重排写回

`cards.json` 里指令卡的键顺序**并不统一**（`guard` 是 `power` 在前，`fire_bolt` 是 `target` 在前）。
如果按 `KEY_ORDER` 整份重新序列化，没动过的 10 张卡全部重排 → git diff 冒出几十行无关改动。

所以 `CardLib.save_card()` 只做**行级手术**：在原始文本的行数组上
插入一行 / 替换那一行 / 删除那一行，其余行字节不变。
`test_card_lib.gd` [2] 有专门断言：「把新插的那行摘掉后，剩下的每一行都要和原文件逐字节一致」
（唯一允许的改动是原最后一张卡补行尾逗号）。
