## 2. 角色与纪律（重要）

- **学员写 `src/core/*.gd` 实现；agent 只做**：code review、答疑、出题、解释 API、跑测试验收、指设计问题。
- agent 默认负责：`docs/`、`tests/`、`data/`、`tools/`、CI、git 提交与推送。
- **不许为了变绿改测试/数据**；改测试必须同步文件末尾 `EXPECTED_CHECKS`。
- `tests/pending/` 不进 CI、不进主套判定；**全绿后 `git mv` 到 `tests/` 才启用**。
- 提交前必须全绿（`run_tests.bat` 退出码 0 + 无 `[FAIL]` + 无 `SCRIPT ERROR`）；CI 还会跑 `tools/validate_data.gd`。
- **`run_tests.bat` 是唯一的验收入口**，分三段：
  - **PART 1 主套**（`tests\*_test.gd`，四重判定：PASS + 无 `[FAIL]` + 无 `SCRIPT ERROR` + 无 `[HUNG]`）
  - **PART 1.5 待启用基线**（`tests\pending\*_test.gd`）：每个文件打一行 `[READY  ] name  N checks --> git mv ...`
    或 `[PENDING] name  N checks / M failed`，**只报告、永不判失败**。跟主套结果同一个终端，不用去别处翻。
    第三种结果是 `[HUNG   ] name  killed on timeout -- infinite loop, no verdict available`（见 §22）
  - **PART 2 详细自检**（`tools/preflight.ps1`，**13 或 14 项，看工作区脏不脏**）：数据校验 / `has_acted` 残留 / `EXPECTED_CHECKS` /
    兵科覆盖 / **平衡冒烟 100 场** / 脚本编码 / 工作区噪音 / 等。
    第 [7] 节「工作区噪音」在**干净工作区**走 `Say-Ok`（计 1 项 → **14 项**），有未提交改动时走 `Say-Info`（不计数 → **13 项**）。
    **两种读数都正常**，别当成回归；验收阶段必然带未提交改动，所以看到 13 项是对的。
  三段都过才打印 `===== ALL GREEN =====`；只想跑详细自检用 `tools\preflight.bat`。
  **每个单文件跑都有 90 s 硬性超时**（§22）：超时就杀掉进程并在日志尾部写 `[HUNG]`，
  不会再把整场测试无限期卡住。看到 `[HUNG]` = 测试或被测代码里有死循环，不是环境问题。
  脚本化调用（CI、agent）加 `set NO_PAUSE=1`，结尾就不会停在 `pause` 等按键。
- 提交信息用「类型(范围): 中文摘要」，多行用 `git commit -F <文件>`，文件用 **UTF-8 无 BOM**；写 `.bat` 要 CRLF + 纯 ASCII。
- 测试脚本的 Godot 路径是**相对仓库**解析（`run_tests.bat` / `check.ps1`，可用环境变量 `GODOT` 覆盖），不要改回绝对路径。
- **每个任务开工前先报预计用时**（学员和教练都要）：格式 `预计 X–Y h（依据：§NN 任务卡难度 ★★★ + 预计行数 N）`。
  出处是 `docs/implementation-tasks.md` 进度总览表里的「预计用时」列；做完后回头对一下实际用时，
  偏差超过 2 倍就在复盘里记一句原因（估错的往往是没算"卡在某个 GDScript 语义上"的时间）。
  **2026-11-25 实测校准**：学员当天做完 M3.1 收尾 + M3.2 + M3.3 三块，**实际编码合计只有 3–4 h**，
  其余时间全在等 agent 反馈（写→跑测试→贴报错→等 review→再改）。所以表里的区间现在读作「乐观上限」，
  未完成的块已按下修后的倍率改过；真正决定日历进度的是**返工轮数**，不是打字速度。

### 2.1 工作方式约定（2026-11-25 起，接手的 agent 也要遵守）

学员对 agent 的工作方式有明确要求，四条：

1. **同一轮内并行发工具调用**：读多个互不相关的文件、搜多个关键词、查多个接口时，一次性全发出去，
   **禁止逐个串行**。验收跑测（主套 + 数据校验 + 平衡冒烟 + 独立 worktree 复验）也是同一批发出。
2. **`subagent` 收结论，不收过程**：探索性、可隔离的工作（调研、审查、独立实现一份参考实现）
   下发给子 agent，主上下文只回收结论与文件路径，不把原始过程（大段日志、逐行 diff）带回来。
   - 隔离靠 **独立的 `git worktree`**：给每个子 agent 分一个互不重叠的目录（如 `_ref_m35` / `_ref_m37`），
     各自只改自己那份，主工作区不动。
   - **把子 agent 当「coding 工具」而不是「同事」**（2026-11-25 校准）：不要让它自己读一堆文档去理解项目，
     那既慢又费 token。正确做法是**主 agent 先把规格啃完**，然后给它**函数级指令**：
     写哪个文件、加什么函数签名、插在第几行附近、边界条件是什么。子 agent 只负责敲代码，
     **正确性由主 agent 事后核验**（复核 diff + 独立跑测试 + 故意改坏看测试是否变红）。
   - **按难度调思考强度**：小块/机械改动（加个加载函数、补个谓词）可以把子 agent 的
     `reasoning_effort` 调低甚至关掉，模型本身也选小的；只有需要自己摸清调用链的活才给高思考。
3. **`workflow` 做同构批量**：存在几十个同构子任务时（批量扫描全仓、批量迁移、多角度分析），
   写成编排脚本一次性并行分发，不要一个个 `subagent` 排队。
4. **长命令走后台 job**：构建、全量测试、平衡模拟、push 重试等长命令用后台跑（`run_in_background`），
   不要阻塞等待；先去推进其他工作，需要结果时再统一收割（`job_output`）。
5. **给学员「思路」，不给「成品代码」**（2026-11-26 校准，学员原话：「以后请提供给我思路而不是
   直接贴给我一段代码」）。作业单写到这个粒度就够：规则是什么、三个对象各自手上有什么、
   有哪几条路可选、各自的代价、判据是什么、坑在哪。**函数体让学员自己写。**
   - 例外：**签名**可以给（`stat_mod(stat: String, table: StatusTable) -> int`），因为签名是接口约定；
     但循环体、条件判断这些实现细节不要给。
   - 必须解释**为什么**这么选（例如「认 `b.kind` 但不硬编码数值，否则改 JSON 不跟随」），
     而不是只给对的写法 —— 只给答案等于替学员做题。
   - 与第 2 条的区别：第 2 条说的「函数级指令」是给**子 agent（coding 工具）**的；
     第 5 条是给**学员（人，在学 GDScript）**的。对象不同，粒度也不同，别混。

**一条实测校准**：本机 `node` 不存在，所以 `create_worktree` 工具必失败，隔离树一律用
`git worktree add --detach <路径> <commit>`，用完 `git worktree remove --force <路径>`。

### 8.1.1 本轮踩到的两个「看起来对、实际反了」的坑（下次容易再犯）

**① `_mulligan_of()` 的语义是「已用过」，不是「还能用」**
```gdscript
func _mulligan_of(owner:String) -> bool:
	return mulligan_used if owner == "player" else enemy_mulligan_used
```
守卫写成 `if _mulligan_of(owner) == false: return false` 会**恒成立**（开局时标记就是 false），
于是 mulligan 一次都执行不了。正确写法是 `if _mulligan_of(owner): return false`。
**教训**：把复合守卫拆成三条独立 `if`，别挤在一个 `||` 链里 —— 挤一起时方向反了很难看出来。

**② Nil 判空的方向写反**
```gdscript
if board.find_first_unit("front"): break   # ❌ 有目标反而退出
if tgu == null: break                      # ✅ 没目标才退出
```
写反后 `battle_m2_test` 的「敌方支援线单位打不到 HQ，就打我方前线单位」会红
（期望 HQ/单位受伤，实际一点没打）。**教训**：判空的条件要跟着"没有目标"写，而不是跟着变量名想当然。

**③ GDScript 参数是值传递，写 `swap(a,b)` 无效**
```gdscript
func swap(a, b) -> void:
	var tmp = a
	a = b
	b = tmp
```
调用 `swap(dck[i], dck[j])` 只交换局部副本，`dck` 完全不变 —— 洗牌变成空操作，
而且**测试可能测不出来**（`_draw_into` 从牌库头部取牌，换回尾部的牌即使不洗也会换出手牌）。
**教训**：数组元素交换必须在持有数组的上下文里直接下标赋值。

**D5 正确形状**（`_begin_turn()` 必须在 `if` 外，两条分支都走）：
```gdscript
func begin_first_turn() -> void:
	opening_phase = false
	if first_move == "enemy":
		_enemy_turn()
	_begin_turn()
```

**D6 正确形状**：`mulligan()` 守卫顺序 = `not opening_phase` → `cards.is_empty()` →
`owner=="player" and mulligan_used` / `owner=="enemy" and enemy_mulligan_used` → 每张都在自己手牌里
（否则 false）；然后 erase → 追加回该 owner 的牌库 → 置 used 标记 → `_shuffle_rng()` → `_draw_into(owner, cards.size())`。
`_shuffle_rng` 必须自己写 Fisher-Yates（`RandomNumberGenerator` 没有 `shuffle`，`Array.shuffle` 不可复现）：
```gdscript
func _shuffle_rng(arr: Array) -> void:
	for i in range(arr.size() - 1, 0, -1):
		var j: int = rng.randi_range(0, i)
		# swap arr[i] / arr[j]
```

### 14.2 本轮修掉的 3 处**测试**缺陷（教练的活，学员不用管）

> 这三条都是「测试自己写错了」，会让**错误实现也变绿**，或者让**正确实现永远红**。

**① `deck_build_test.gd` [3]：独立性断言恒真**
```gdscript
_check(p != e or p.size() == e.size(), "两次加载互不影响（不是同一个数组引用）")  # ❌
_check(not is_same(p, e), "两次加载不是同一个数组引用")                          # ✅
_check(not is_same(p[0], e[0]), "展开后的 Card 对象也不共享引用")                # ✅ 新增
```
`or` 后半句在正常实现下**永远为真**（双方都是 39 张），整条断言无论前半句真假都通过。
实测：故意写一个「返回同一个共享数组」的错误实现，旧断言照绿，新断言立刻红。
注意 GDScript 里 `Array` 的 `==` 是**内容比较**（`[1,2,3] == [1,2,3]` 为 true），判引用同一性必须 `is_same()`。

**② `deck_build_test.gd` [4]：「总数不对」用例从没测到总数分支**
原来写 `[{ "id": "footman", "count": 10 }]`，它**同时**违反同名上限（4），而实现里同名检查在总数检查**之前**
→ `push_error` 打的是「同名卡 footman 超过上限 4（10 张）」，**总数校验从未执行**（日志已实证）。
改成 37 张、每个 id 合法、同名都不超 4 的牌组，日志确认命中 `牌组张数必须 = 39（实际 37）`。
`EXPECTED_CHECKS` 10 → **11**。

**③ `stat_mod_test.gd` [5][6]：`b.end_turn()` 会真的跑敌方 AI**
```gdscript
var tgt := _target(b)      # 放 enemy_support
b.end_turn()               # ← 敌方 AI 真的跑一遍，把靶子挪到 front 0 号格
var atk := _atk(b)         # 放 front 1
b.attack_unit(atk, tgt)    # ← 两者同线，跨度 0 → 直接返回 false
_check_eq(tgt.hp, 7)       # ← 血量没变，红
```
**这条测得不是「buff 失效」，而是「攻击被拒」**。参考实现怎么改都过不了，因为根本不是实现问题。
修法：靶子直接放 `front`（AI 不会再挪它）、攻击者放 `player_support`（与 front 相邻，跨度 1），
并**补一条 `_check(b.attack_unit(atk, tgt), "buff 失效后攻击成立（防空跑）")`**。
`EXPECTED_CHECKS` 6 → **7**。

### 14.5 2026-11-26 二次修假绿：非法用例「同时违反两条规则」

`deck_build_test` 开 M3.5 前重跑五条反假绿探针，**探针 ② 暴露了测试漏洞**（实现照绿）：

| 探针 | 结果 |
|---|---|
| ① `total != DECK_SIZE` → `total > DECK_SIZE` | ✅ 红「总张数不是 39（期望 0，实际 37）」 |
| ② `MAX_SAME_CARD := 4` → `5` | ❌ **仍 11/11 全绿 = 假绿** |
| ③ 所有 Card 共享同一对象 | ✅ 红 2 项（`footman 期望 4 实际 39`、`guard 期望 3 实际 0`） |
| ④ 非法时仍继续展开 | ✅ 红「总张数不是 39（期望 0，实际 37）」 |
| ⑤ `if count <= 0:` → `count < -100:` | ✅ 红「count <= 0 → 空数组（期望 0，实际 39）」 |

**根因**：`bad_dup` 原写 `[{footman,5},{archer,34}]` —— footman 超名字上限、**archer 34 也超**，
两条同时违规；放宽 footman 上限后 archer 仍然触发拦截，断言照样通过 ⇒ **从没测到「同名上限」这一条**。
`bad_count` 原写 `[{footman,0}]` 同病：count 0 让总数变 0，同时违反「总数必须 39」。

**修法（三个非法用例全部重写成「只违反一条规则」，项数仍是 11）**：
- `bad_total`：37 张、每 id 合法、同名都不超 4（保持原样）。
- `bad_count`：`footman 0` + 其余 9 种各 4 + `fire_burst 3` = **39 张**，只违反 `count > 0`。
- `bad_dup`：`footman 5` + 其余 8 种各 4 + `guard 4` + `mend 2` = **39 张**，只违反同名上限。

**通用教训（比这三条用例更重要）**：**每个非法用例必须「只违反一条规则」**。
否则你把那条检查从实现里删掉，测试都不会红 —— 测的不是你以为的那条。
验证手段只有一条，和 §14.3 一样：**故意把实现改坏，看测试会不会红**；绿了就说明用例有重叠。

### 16.4 `.tscn` 手写最小结构（M4 全阶段沿用的约定）

`tools/unit_maker.tscn` 只有 14 行：一个根 `Control` + 一个 `script` 引用，**所有控件都在 GDScript 里建**。

```
[gd_scene load_steps=2 format=3 uid="uid://cunitmaker0001"]
```

### 16.6 行级手术：为什么不能整份重排写回

`cards.json` 里指令卡的键顺序**并不统一**（`guard` 是 `power` 在前，`fire_bolt` 是 `target` 在前）。
如果按 `KEY_ORDER` 整份重新序列化，没动过的 10 张卡全部重排 → git diff 冒出几十行无关改动。

所以 `CardLib.save_card()` 只做**行级手术**：在原始文本的行数组上
插入一行 / 替换那一行 / 删除那一行，其余行字节不变。
`test_card_lib.gd` [2] 有专门断言：「把新插的那行摘掉后，剩下的每一行都要和原文件逐字节一致」
（唯一允许的改动是原最后一张卡补行尾逗号）。

### 18.3b S2 的三档定义（施工用的精确表）

「HQ > 没被保护的非 Guard > Guard」落到代码就是三个桶，每个敌方单位**恰好**进一档或一档都不进：

| 档 | 装什么 | 判定式子（按此顺序写） | 理由 |
|---|---|---|---|
| **0** | 敌方 **HQ** | `var hq := _opposite_hq(owner)`；`if hq != null: out.append(hq)` | 打掉 HQ 直接赢。**HQ 被 Guard 保护也照样进档 0**，让 `attack_unit` 去拒，拒了自动落到档 1/2 —— 这就是 S1 的实现方式 |
| **1** | **不受保护的非 Guard** | `if u.is_guard(): guards.append(u)  elif not _is_guarded(u): out.append(u)` | 打它必成功，当前最大收益 |
| **2** | 敌方 **Guard** | 同上的 `guards` 数组，最后 `out.append_array(guards)` | Guard 之间互不保护（§32），打 Guard 一定合法；放最后是因为通常高防 |

**排除项（一档都不进）**：己方单位（`u.owner == owner`）、空槽（`u == null`）、
HQ 节点重复入线（`u.is_hq`，HQ 已由档 0 单独加）、**被保护的非 Guard 单位**
（`_is_guarded(u) == true` 且 `not u.is_guard()` → 这就是 S3 的落地方式）。

**⚠️ 必须先判 `is_guard()` 再判 `_is_guarded()`**：`_is_guarded()` 第一行就是
`if target.is_guard(): return false` —— Guard 自己永远不算被保护。写成
`if not _is_guarded(u): out.append(u)` 再 `elif u.is_guard(): ...` 的话，Guard 会被错分进档 1、
档 2 永远为空，S2 的「Guard 最后打」直接失效，`ai_guard_test` [4] 会红。

**档内不排序**：同一档按 `units_in()` 的返回顺序（格子下标升序）拼，稳定可复现、无比较函数可写错。
要改优先级只改档位归属，别加档内排序。**拼装顺序**：档0 → 档1 → 档2，用 `append_array` 依次拼。

### 18.5 学员问过的两个技术问题（2026-11-26 实测答复）

**Q1：Godot 有没有 C++ `priority_queue` 那样的数据结构？**

没有。实测 `ClassDB.class_exists()` 对 `PriorityQueue` / `Heap` / `BinaryHeap` / `MinHeap` / `MaxHeap`
全为 `false`；`ClassDB.get_class_list()` 里名字含 heap/priority/queue 的类**一个都没有**。
`Array` 上跟有序沾边的只有 `sort_custom` / `bsearch_custom`。

但**这块不需要堆**，因为规模根本不到（实测 `Time.get_ticks_usec`）：

| 操作 | 单次耗时 |
|---|---|
| 扫三条线收集敌方单位 | 12.63 µs |
| 复制 + `sort_custom` 排 15 项 | 36.08 µs |
| 三桶 `append`（不排序） | 9.73 µs |

一局 ≈ 26 次 AI 调用，200 局 = 5200 次 → 全盘扫一遍总开销 **≈ 66 ms**。
堆的 O(log n) 优势要 n 到几千，这里候选目标上限 **14 个**（15 格 − 2 HQ）。
S2 只有 3 档 → **三个桶一次遍历分档**，O(n) 且天然稳定，比 `sort_custom` 更快更不容易写错。

**顺带一个坑**：`sort_custom` **不是稳定排序**，而且边界不高 —— 实测全同优先级输入
n=14/15/16 保持原序、**n=17 起开始乱序**。棋盘上限 14 碰不到，但这是运气不是保证。

**Q1b：每次重建一份目标清单，是不是比「放置单位时按序插入」更劣？（2026-11-26 更正）**

**是的，增量插入更快 —— 我第一版答错了。** 第一版比的是「重建一次」vs「从零按序插入 n 次」，
对增量不公平（增量方案整局只建一次，之后靠增删维持）。按真实生命周期
（26 次查询 / 8 次部署 / 6 次死亡每局）重测：

| n（在场敌方单位） | A 每次重建 µs/局 | B 增量插入 µs/局 |
|---|---|---|
| 3 | 81.9 | 39.4 |
| 6 | 102.3 | 50.1 |
| 9 | 122.3 | 61.4 |
| 12 | 169.0 | **66.4（2.5× 更快）** |
| 13 | 147.7 | 82.5 |

**但最终仍选 A（每次重建）**，理由是那三条而不是性能：①绝对差 = 单局 4.7 ms 里的 2%；
②B 的档位依赖 `_is_guarded()` 每次现算，Guard 一死邻居立刻变档，B 必须重算所有邻居，
等于把规则再造一遍；③A 无状态永不算错，B 漏一次更新就是永久错误。

**这条教训要记住**：性能问题先从**真实生命周期**算总账，别拿「单次操作 × 次数」自证 ——
我第一版就是被这个假口径带偏的。完整的两个方案对比写在
`docs/implementation-tasks.md` §39.1b（原有独立文档已并入，引用同节）。

**Q2：场上有两个相同单位，会不会删除误删 / 指令打错？**

不会。实测 `Unit`（`RefCounted`）的 `==` 比的是**引用**不是内容：

```
两个独立对象（id/hp/attack 全同）：a == b = false
同一个引用：                      a == c = true
```

`Board.position_of()` 用 `slots[l].find(unit)`，`Array.find/erase/has` 也走引用 → 各认各的。
四个场景实测全对：两个 `dup` 分放 `front/1` 与 `front/3` 时 `position_of` 各返回各的；
`remove(u1)` 只清 `front/1`；`attack_unit(atk,t1)` 后 `t1` 掉血 `t2` 不变；
两张内容相同的 `Card` `erase(c1)` 只删 `c1`。

**但有两个真实地雷（都已登记，不是本块的活）**：

1. `Board.place()` **不检查「这个单位已经在场上」**，同一个对象可占两个格。
   实测 `place(u, front/1)` 与 `place(u, front/3)` 都返回 true，`position_of(u)` 只返回第一个，
   随后 `remove(u)` 只清 `front/1`，`front/3` 留下一个**查不到位置的残影**。
   → 测试辅助必须 `assert(place(...))`（`ai_guard_test` 已这么写）；生产代码 `_deploy_unit()` 每次
   `Unit.from_dict(...)` 新建对象，撞不上。
2. `Battle.setup()` 里 `enemy_deck` 与 `deck` 是**同一批 `Card` 对象**（`for i in p_deck` 双向 append）。
   实测 49 张全共享。现在不炸是因为 `Card` 是只读模板 + `erase` 按引用删；
   **以后给 `Card` 加任何可变状态**（升级/临时减费/附魔）就会一方改动同时改到另一方。
   → 别在 AI 这块给 `Card` 加字段；真要加，单开一块做 `setup()` 里 `Card.from_dict()` 深拷贝。

**另一个非逻辑问题**：日志只打 `display_name`，两个同名单位在日志里看起来完全一样。
现在不影响正确性，等 M4 做界面时再处理（UI 有格子坐标，天然可区分）。

### 19.2 同屏多张卡会互相串色 —— 真 bug，不是假想

**旧代码**：

```gdscript
var sb := get_theme_stylebox("panel")   # ← 拿到的是主题里那一份共享的 StyleBoxFlat
var flat: StyleBoxFlat = sb
flat.bg_color = ...                     # ← 原地改 = 改主题
```

`Theme` 返回的 stylebox 是**共享资源**（探针实测：两个 `PanelContainer` 从同一 `Theme` 拿到的
`panel` stylebox `is_same == true`）。单张预览完全看不出来，但 M4 手牌区一次显示 5 张时，
**最后一张会把前面所有卡刷成自己的颜色**。

**修法**：每个 `CardView` 在 `_build()` 里自建私有 `_flat := StyleBoxFlat.new()`，
再 `add_theme_stylebox_override("panel", _flat)`。

**反向验证**（这一步不能省）：

| 实现 | `test_card_view.gd` 结果 |
|---|---|
| 旧写法（`get_theme_stylebox` 后原地改） | **3 项红**（正是 [2] 组的三条独立性断言） |
| 新写法（私有 `StyleBoxFlat` + override） | **7/7 PASS** |

如果只跑"改完是绿的"而不跑"改回去会红"，就无法排除"这几条断言其实恒真"。

### 20.4 本轮值得记的三条

1. **结构根因不是「忘了三个桶」，是「拿局面归属当开关」**。`if front 归我 / elif front 归敌` 看起来像在分派，
   实际是在用「谁占着前线」代理「谁能打到谁」——同一条前线上，近战/空军/炮兵的能打范围完全不同，
   这个信息只在 `_line_span_to` 和 `attack_unit` 里。**能打的判定权必须留在 `attack_unit`，AI 只负责排清单。**
2. **死循环不会报错，只会让你以为测试坏了**。判据要分两步：先要「能跑完并打印」（哪怕 6 红），再要「14 绿」。
   把这两步混成一步，就会去怀疑 Godot/环境而不是自己的 `while`。
3. **`Array[Unit]` 的返回类型是运行期检查，不是编译期**。从 `Dictionary` 里掏出来的 `[]` 是无类型 `Array`，
   返回时既不报编译错、也不在 `--check-only` 里暴露，只在**真跑到那一行**时打 SCRIPT ERROR 并把内容丢掉。
   写这段代码时**不要让桶经过 Dictionary**，直接声明两个类型化数组。

### 21.2 `git push` 的前置条件（本机踩过，别重复踩）

remote 是 `ssh://git@ssh.github.com:443/...`（**不是** 22 端口的 `github.com`）。首次推送会报
`Host key verification failed` / `Could not read from remote repository`，原因是两处本地状态都缺：

1. `~/.ssh/known_hosts` 里没有 `[ssh.github.com]:443` 的主机公钥 →
   `cmd /c "ssh-keyscan -p 443 ssh.github.com 2>nul >> %USERPROFILE%\.ssh\known_hosts"`。
2. `~/.ssh/config` 只有 `Host github.com` 一条，`ssh.github.com` 拿不到 `IdentityFile` / `IdentitiesOnly` → 补一段
   `Host ssh.github.com` / `HostName ssh.github.com` / `Port 443` / `User git` / `IdentityFile ~/.ssh/id_ed25519_github` / `IdentitiesOnly yes`。

## 22. `run_tests.bat` 的悬死保护（2026-11-27，教练侧）

### 22.1 为什么要加

学员当前的 WIP 里有一个**死循环**（§20.2 第一行）。死循环和「测试红」是两种完全不同的故障：

- 红的测试会**跑完、打印、给行号**；
- 死循环**什么都不打印、永远不退出**。原来的 `run_tests.bat` 会无限期卡住，
  看起来像「Godot 起不来」或「环境坏了」，实际是测试脚本在转圈。

一次真实的现场：直接跑 `ai_guard_test`，**120 秒零输出**；`run_tests.bat` PART 1 卡在该文件上，
整场测试没有结论。**一个你无法跑完的红基线，比红基线本身更糟。**

### 22.2 改了什么

`run_tests.bat` 新增子过程 `:run_godot <res-script> <logfile> <timeout-seconds>`，
用 PowerShell 的 `Start-Process -PassThru` + `WaitForExit(ms)` 做硬性墙钟超时：

| 位置 | 超时 | 理由 |
|---|---|---|
| PART 1 主套（`:run_one`） | **90 s** | 主套 18 个文件每个实测都在 20 s 内，90 s 是很宽的余量 |
| PART 1.5 pending（`:pending_one`） | **90 s** | pending 正是学员改到一半的地方，最可能转圈；统一 90 s 便于记 |

超时后：`$p.Kill()` → `WaitForExit()` 等进程真正退出 → `Dispose()` → 停 300 ms → 用 `[IO.File]::AppendAllText`（UTF-8 无 BOM）追加一行 `[HUNG] godot did not finish within 90s and was killed` → 退出码 3。
两个 `findstr /C:"[HUNG]"` 检查把它当失败处理：

- PART 1：`[HUNG]` 命中即该文件 `BAD=1`，日志整份 dump，汇总里 `SOME TESTS FAILED`；
- PART 1.5：走独立的 `:pending_hung` 分支，打印
  `[HUNG   ] <名>  killed on timeout -- infinite loop, no verdict available`
  外加**被杀前最后 5 行**（通常能看出卡在第几个用例）。**不并入 `[PENDING]` 计数**——
  `[PENDING]` 的含义是「跑完了、红了 N 项」，`[HUNG]` 是「根本没跑完」，两者混淆会误导判断。

同时把 `%~2.err`（Godot 的 stderr）非空时追加进日志：Godot 有些错误只走 stderr，
原来的 `> "%LOG%" 2>&1` 在批处理里偶尔会丢。

### 22.3 踩到的批量坑（写 `.bat` 必看）

- **`echo` 文本里的括号会终止 `if (...)` 块**。第一次写 `echo ---- killed on timeout (infinite loop?) ----` 时
  报 `---- was unexpected at this time.`，整段 `if` 块被打断。批处理里 `echo` 内容含 `(` `)` 必须转义或干脆避开。
- **`%RG_RC%` 必须在 `exit /b` 之前落成变量**。`powershell ... ` 之后立刻 `if errorlevel` 会被
  后续的 `if exist (...)` 覆盖掉 `errorlevel`，所以先 `set "RG_RC=%errorlevel%"` 再判。
- **`Kill()` 后立刻 `Add-Content` 会报 `Stream was not readable`**。子进程虽然被杀了，但
  `-RedirectStandardOutput` 的重定向句柄还没释放，PowerShell 这时打开同一个文件写入会失败，
  错误直接以红字打在被杀报告上方（实测出现过，很误导人）。修法：`Kill()` 之后必须
  `WaitForExit()` + `Dispose()`，再 `Start-Sleep -Milliseconds 300` 让句柄释放，最后改用
  `[IO.File]::AppendAllText`（不复用 `Add-Content` 的对象）。
- **批处理里调 PowerShell 输出的中文会乱码**（本机 codepage **936 GBK**）。`chcp 65001` 只影响
  `cmd` 自己，`powershell -Command "...Get-Content ..."` 子进程的**输出编码**仍是系统 ANSI，
  中文经管道就变成 `AI 閫夌洰鏍囷紙Guard锛?`。修法：命令开头加
  `[Console]::OutputEncoding=[Text.Encoding]::UTF8;`。注意 `-Encoding UTF8` 只管「读」，
  不管「写」，两者都要管。
- 改完必须验编码：`.bat` 要 **CRLF + 纯 ASCII + 无 BOM**。本轮实测 `8940 B / 199 CRLF / 0 bare LF / 0 non-ASCII / no BOM`。
  用 PowerShell 的 `[IO.File]::ReadAllBytes` 逐字节数一遍，比肉眼可靠。
- **`.ps1` 反过来必须带 UTF-8 BOM**，这是本轮踩到的新坑。PowerShell 5.1 读**无 BOM** 的脚本时按系统 ANSI
  （本机 936）解码，中文全变乱码，然后报一串**看起来完全不像编码问题**的语法错：
  `表达式或语句中包含意外的标记"}"` / `缺少右"}"` / `意外的标记"妫€鏌ョ偣锛坽1"`…… 实测 `tools/check.ps1`
  因为 `edit` 工具写回时丢了 BOM，直接 28 条 parse error，而 `tools/preflight.ps1`（带 BOM）0 条。
  **自查手法**：`PSParser::Tokenize` 前显式用 `[Text.Encoding]::UTF8` 读文本，0 error 才说明代码本身没错。
  结论：`.bat` 无 BOM、`.ps1` 有 BOM、`.gd` / `.md` 无 BOM 全 LF。

### 22.4 现状（2026-11-27 实测）

```
[PASS] × 18 主套
[HUNG   ] ai_guard_test  killed on timeout -- infinite loop, no verdict available
[详细自检] PASS（13 项通过、0 条提醒）
===== ALL GREEN =====  18 file(s) passed.
===== note: 1 pending test(s) still red -- details above in PART 1.5 =====
```

即：**主套是绿的、pending 是挂的**，和「学员 WIP 有死循环、其余无影响」的诊断完全吻合。
这句话以后可以直接当诊断用——主套全绿 + pending `[HUNG]` = 学员代码里有死循环，不是环境问题。

**同一个坑 `tools/check.ps1` 原来也有**（它的 `Invoke-GodotScript` 用 `cmd.exe /c` 同步跑，没有超时）：
实测直接跑 `tools\check.bat` 会在这个死循环上**挂满两分钟以上不返回**，最后被 agent 那边强制杀掉，
用户看到的就是「工具卡死了」。已同步修好：`Invoke-GodotScript` 加 `-TimeoutSec`（默认 90），
改 `Start-Process -PassThru` + `WaitForExit(ms)`，超时杀进程 + 追加 `[HUNG]`；
主套表格新增 `HUNG` 裁决（不再把「没跑完」误记成 `FAIL` 并丢掉项数），
pending 段落新增 `[挂死] <名>：90 s 内没跑完，进程已杀（死循环？）→ 无裁决` + 后 5 行。
**结论：所有跑 Godot 的入口都必须有墙钟超时，一处漏了就等于整条工具链会卡死。**

对着敌方 HQ 反复调用 `attack_unit`，没成功就再来一遍』」，并解释 `continue` 在 `while` 里的语义。

### 22.7 agent 侧的工具调用也要守 90 s（2026-11-27 用户明确要求）

§22.1–§22.4 说的是**脚本自己**要有超时；这条说的是**agent 调工具时的等待上限**，两者是同一条纪律的两端：

- **凡是「等结果」的工具调用，超时一律写 90 s**（`timeoutMs: 90000` / `timeout_ms: 90000`）。
  不要写 300 s、不要写「默认值」、不要靠工具自身的上限兜底。
- **跑不完就转后台 job**，用 `job_output` 分段收割，而不是把一次调用的等待时间拉长。
  后台 job 的等待同样给 90 s，超时就再收一次——**单次等待永不超过 90 s**。
- 理由：用户 2026-11-27 明确要求「脚本等待最长 90s，挂住的脚本不要一直等、转到后台」（m00629）。
  一次调用卡住 5 分钟，用户看到的就是「工具死了」，和 §22.1 里 `check.ps1` 挂死两分钟是同一种体验。
- 与 §22.1 的对应关系：脚本内的 90 s 是**保护工具链**，agent 侧的 90 s 是**保护交互**。
  两者用同一个数字，是因为「90 s 还没出结果」在两种场景下的结论一样：**它在转圈，得换个跑法**。

## 24. M3.4 卡池块开工：`balance_sim` 对卡池零敏感（2026-11-27 实测）

### 25.3 两个数字口径（下次别再怀疑）

1. **`[详细自检]` 是 13 项还是 14 项，取决于工作区脏不脏。**

   已 A/B 实测（临时 `git checkout --` 掉 `cards.json` 重跑）：干净 = 14 项、还原 = 13 项。
   **验收阶段必然带未提交改动，13 项是对的**；提交后重跑会变 14 项。
2. **`balance_sim` 两套数字都对，差别只在 seed。**
