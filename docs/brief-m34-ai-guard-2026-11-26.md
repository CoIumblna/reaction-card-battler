## §1 病灶定位（自己去看代码，位置已给）

`src/core/battle.gd` 的 `_ai(owner)` 里，攻击段落现在是**两个互斥分支**：

| 分支条件 | 现在的做法 | 病灶 |
|---|---|---|
| `board.has_unit_of("front") == owner` | 循环前线单位，**一律** `attack_unit(u, _opposite_hq(owner))` | HQ 被 Guard 保护 → `attack_unit` 返回 false，**返回值没人接**，这个单位就白过了。既不换目标，也不报错，连日志都没有 |
| `board.has_unit_of("front") == _opposite(owner)` | `find_first_attackable("front", owner)`；为 null 就 `break` | `find_first_attackable` 的筛法是「**不是 Guard**」。对方前线只有 Guard 时返回 null → 直接 `break`，全队白过 |

对比 `tests/guard_test.gd` 第 8 项（已绿）：`attack_unit` 拒绝被保护目标是**正确行为**。
问题在 **AI 侧的选目标策略**，不在 `attack_unit`。

## §2 规则（要做到什么）

| 编号 | 规则 |
|---|---|
| S1 | AI 的单位**只要还有合法目标，就必须真的打出去**，不允许空过一整个回合 |
| S2 | 选目标优先级：**敌方 HQ（可达且没被保护）> 没被保护的非 Guard 单位 > Guard 本身** |
| S3 | 被 Guard 保护的友军**永远不该被 AI 选成目标**（打了必被拒 = 白扔） |
| S4 | Guard 本身**永远是合法目标**（`guard_test` 第 4 项已定：Guard 之间互不保护） |
| S5 | `_is_guarded()` 对不在场上的单位返回 `false`，**不能崩** |
| S6 | 目标清单要扫**全部三条线**，不能只扫 `front` —— 这是「越线攻击」能成立的前提（见 §2.1） |

### §2.1 顺手要说清的一件事：现有 AI 的**目标覆盖面**本身就有缺口

你说「当前 AI 只会打相邻阵线单位」——实测比这个更窄。现有 `_ai()` 的两个分支加起来，
能选的**全部**目标只有两种：

1. 对方 **HQ**（在对方支援线 0 号格）；
2. 对方 **`front` 线上的单位**（第二分支 `find_first_attackable("front", owner)`）。

对方**支援线上的普通单位**（1–4 格）从来没进过候选 —— 哪怕 `attack_unit` 完全打得着。
实测（`tools` 里临时探针，已删）：

```
局面：我方单位(atk 3) @ front/2，敌方普通单位(hp 10) @ enemy_support/2
_line_span_to(front → enemy_support) = true        ← 能打
attack_unit(我方, 敌方后排)          = true        ← 能打

跑一次 _ai("player")：
  敌方后排普通单位 hp：10 → 10     ← 完全没被碰
  敌方 HQ hp：          5 → 2      ← 只打了 HQ
```

所以加「扫三条线」的目标清单**不只是重构**，它顺手把这块可见性补上了 ——
这也正是你说的「方便处理越线攻击」的实际价值：空军（`is_air()`）能打支援线对穿，
以后加空中单位时，同一个清单直接就能用，不用再改 `_ai()`。

> ⚠️ **但注意 S2 的排序会掩盖它**：HQ 排最前且打成功就短路，后排单位照样轮不到。
> 「HQ 永远是第一优先」是**游戏规则层面的取舍**，不是实现细节 ——
> 本轮的 14 项验收测试只要求 S2 按现在这样排，所以**先别改排序规则**。
> 等 M3.8（平衡）真的需要 AI 学会切后排时再单独提，那时改的只是一行档位号。

## §3 三个对象的能力边界（决定这段代码该长在哪）

| 对象 | 有什么 | 没有什么 |
|---|---|---|
| `Board` | `LINES = ["enemy_support","front","player_support"]`、`units_in(line)`、`position_of(unit) -> Array`（**不在场上返回空数组**）、`unit_at`、`find_first_attackable(line, owner)`（筛法=不是 Guard，**不符合 S2 的优先级**） | 不知道怎么算「被保护」——那是 Guard 词条的规则，属于战斗层 |
| `Battle` | `_is_guarded(target) -> bool`（已经是权威判据）、`_opposite_hq(owner) -> Unit`、`_energy_of(owner)`、`attack_unit(attacker, target) -> bool`（**返回真假**，这是关键） | 没有现成的「合法目标清单」 |
| `Unit` | `can_attack()`、`operation_cost`、`is_guard()`、`owner`、`is_hq` | 不知道自己被不被保护 |

两句话结论：

1. **「这个目标能不能打」的权威判据是 `attack_unit` 的返回值**，不是你在外面猜。
   外面猜的每一条规则都可能和它对不上（够不着、被保护、能量不够、同主……）。
2. **`find_first_attackable()` 现在没用**——它的筛法是「不是 Guard」，和 S2 的
   「Guard 是**最后**的候选」冲突。你可以不用它（保留不动，别删，`guard_test` 没断言它）。

## §4 两条可选路线（自己选，各自代价写清）

### 路线 A：给攻击手排一张目标清单，依次试到成功　✅ 已选（2026-11-26）

- 形状：一个私有函数返回「按 S2 排好序的敌方目标数组」，另一个私有函数拿着攻击手遍历这张表，
  第一个 `attack_unit` 返回 true 的就停。
- 优点：**失败的原因完全交给 `attack_unit` 判**，你不用在外面复刻规则 → 以后加新规则（比如 M3.6 的、
  M3.8a 的）这里不用改。
- 代价：每个攻击手都会重建一次目标清单（`units_in` × 3 条线）。棋盘最多 15 格，**这个开销可以忽略**，
  不要为它做缓存。
- 这是参考实现的路线。**已选定走这条**。

#### §4.1 目标清单怎么排序：**别用堆，用三个桶**（实测数据）

你问「Godot 有没有类似 C++ `priority_queue` 的结构」——**没有**。实测 `ClassDB.class_exists()`：

```
PriorityQueue = false   Heap = false   BinaryHeap = false
MinHeap = false         MaxHeap = false
ClassDB 里名字含 heap / priority / queue 的类：一个都没有
```

`Array` 上跟「有序」沾边的方法只有 `sort_custom` / `bsearch_custom`（另 `sort` / `bsearch` 用于原生可比值）。

**但你不需要它，原因不是「实现麻烦」，是规模根本不到**。实测（`Time.get_ticks_usec`）：

| 操作 | 单次耗时 |
|---|---|
| 扫三条线收集敌方单位（`units_in` × 3） | 12.63 µs |
| 复制 + `sort_custom` 排 15 项 | 36.08 µs |
| 三桶 `append`（不排序） | 9.73 µs |

一局约 13 回合 × 2 方 = 26 次 AI 调用；200 局 = 5200 次 → **全盘扫一遍总开销 ≈ 66 ms**。
堆的 O(log n) 优势要 n 到几千才看得出来，这里 n ≤ 14。

而且 S2 的优先级只有 **3 档**（HQ / 没被保护的非 Guard / Guard），
所以最优写法是**三个桶**：一次遍历，按档位分进三个 `Array[Unit]`，最后按档位顺序 `append_array` 拼起来。
O(n)、**天然稳定**、没有比较函数可写错 —— 比 `sort_custom` 又快又不容易错。

#### §4.1b 「每次重建」vs「放置时按序插入维护一份表」—— 你问的这个，我第一版答错了

> 你问：**每次都对敌人单位重建一次桶，是不是比「每次放置单位时按顺序插入」更劣？**
>
> **第一版我答「重建更快」，那个结论是错的。** 我当时比的是「重建一次」vs「从零按序插入 n 次」——
> 增量方案在真实对局里**整局只建一次**，后面靠增删维持，所以那个比法对 B 不公平。
> 按真实生命周期重测后：**B（增量插入）确实更快，你的判断是对的。**

重测口径（`REPEAT=3000` 取平均；`n` = 在场敌方单位数）：

| n | A 每次重建 µs/**局** | B 增量插入 µs/**局** | 谁更省 |
|---|---|---|---|
| 3 | 81.9 | 39.4 | **B** |
| 6 | 102.3 | 50.1 | **B** |
| 9 | 122.3 | 61.4 | **B** |
| 12 | 169.0 | 66.4 | **B（2.5×）** |
| 13 | 147.7 | 82.5 | **B** |

（一局按 26 次 AI 查询、8 次部署、6 次死亡统计。B 的每步代价实测：部署一次 2.0–2.7 µs、
死亡一次 0.5–1.2 µs、移动一次 2.1–3.5 µs；查询时读现成表只要 0.4–0.8 µs，而 A 重建一次要 3.1–6.1 µs。）

**但结论仍然是「用 A 重建」，理由换了三条，而且都不是性能：**

1. **绝对差值小到无意义。** `balance_sim` 实测单局 `run_auto` 平均 **4671 µs**。
   n=12 时 A 是 169 µs/局 = **占 3.6%**，B 是 66 µs/局 = 占 1.4%。
   省下来那 100 µs 在整局 4.7 ms 里是 2%，而 200 局总差 ≈ 20 ms —— 跑步都感觉不到。
2. **B 的正确性成本远高于它省下的时间。** 增量维护要求「棋盘每次变动都记得更新那张表」，
   而这份清单的排序**依赖 `_is_guarded()`（每次现算，不是存的标记）**：
   Guard 一死，它相邻的单位**立刻失去保护**、档位就变了。
   所以 B 不只要在「部署/死亡/移动」时更新，还得在「Guard 死亡」时把它**所有相邻单位的档位重算一遍** ——
   这等于把 `_is_guarded` 的规则在增量路径里再实现一次，两处逻辑迟早不一致。
3. **A 是「无状态」的，永远不会算错。** 每次从棋盘现推一遍，棋盘是什么就给什么答案；
   B 一旦漏了一次更新就变成永久错误（而且要很久以后才被人发现是 AI 行为怪）。

**判据（什么时候该反过来选 B）**：如果单局 AI 调用次数涨到几百次、或者棋盘扩到 30+ 格，
重建的 26×n 会变成主开销，那时候才值得引入增量表，并且**必须同时写测试**
（「连续 20 次随机部署/死亡/移动后，增量表与全量重建的结果逐项一致」，
即拿重建当 oracle 做差分测试）。现在规模不到，不要提前优化。


#### §4.2 一个必须知道的坑：`sort_custom` **不是稳定排序**

如果你还是想用 `sort_custom`，注意它**不保证同优先级元素保持原顺序**，而且乱序的**触发边界不高**。
实测（全同优先级输入，稳定性判据 = 输出是否等于输入顺序 `[0,1,2,…]`）：

```
n=14  保持原序=true     n=15  true     n=16  true
n=17  保持原序=false ← 从 17 个开始就不稳定
n=18  false             n=20  false
```

第 17 个元素就开始乱。棋盘上限 14 个目标，**理论上碰不到**——但这是运气，不是保证
（以后加召唤/衍生物/双 HQ 模式就会撞上）。所以：

- 要排序就**显式写 tie-break**（优先级相同再比格子/序号），让比较函数成为全序；
- 或者干脆用 §4.1 的三桶，绕过这个问题。

#### §4.3 这张清单**不要缓存到下一回合**

单位会死、会移动、Guard 被打死会让相邻单位**立刻失去保护**（`_is_guarded()` 是每次现算的，
不是存下来的标记）。所以：

- ✅ 每个攻击手开打前重建一次；
- ❌ 不要在 `_ai()` 开头建一次全队复用；
- ❌ 更不要挂到 `Battle` 的成员变量上跨回合留着 —— 那是典型的「缓存比计算还贵」加上「状态不同步」。

#### §4.4 场上两个「完全一样」的单位会不会互相冒充？—— 实测：不会

`Board.position_of()` 用 `slots[l].find(unit)`，`Array.find` / `erase` / `has` 都不是比内容。
我实测了 `Unit`（`RefCounted` 派生）的 `==` 语义：

```
两个独立对象（id / hp / attack 完全相同）：a == b      = false
同一个引用：                            a == c      = true
                                            is_same(a,b) = false   is_same(a,c) = true
```

`Object` 的 `==` 比的是**引用**，不是内容 → 同名同属性的两个单位在
`position_of` / `remove` / `attack_unit` / `hand.erase` 里都各自独立。实测三个场景全对：

| 场景 | 结果 |
|---|---|
| 两个 `dup` 放 `front/1` 和 `front/3` | `position_of` 各返回各的位置 ✓ |
| `remove(u1)` | `front/1` 变 null，`front/3` 仍是 `u2` ✓ |
| `attack_unit(atk, t1)` | `t1.hp` 10→7，`t2.hp` 仍 10 ✓ |
| 两张内容相同的 `Card`，`hand.erase(c1)` | 只删 `c1`，剩 `c2` ✓ |

**但有一个真实的坑（在你写的代码里，不在 `board.gd` 里）**：`place()` **不检查**
「这个单位是不是已经在场上」，而且**同一个对象可以放进两个格子**。实测：

```
place(u, front/1) = true   place(u, front/3) = true    ← 同一个对象占了两个格
position_of(u)    = ["front", 1]                       ← 只返回第一个
remove(u)         → front/1 变 null，front/3 还留着 u  ← 幽灵：留下一个查不到位置的残影
```

所以验收测试里的 `_place()` 辅助**必须 `assert(place(...))`**（已经这么写了），
生产代码里 `_deploy_unit()` 每次 `Unit.from_dict(...)` 新建对象，不会撞上。

#### §4.5 另一个地雷：双方牌库共享同一批 `Card` 对象

`Battle.setup()` 里 `enemy_deck` 是从**同一份** `p_deck` 逐项 `append` 的：

```gdscript
deck.clear()
for i in p_deck:
    deck.append(i)
enemy_deck.clear()
for i in p_deck:
    enemy_deck.append(i)      # ← 同一个 Card 对象引用
```

实测 `player deck 49 张 / enemy deck 49 张 / 共享同一对象的 49 张`。
目前**不炸**，因为 `hand.erase()` 按引用删、两边删的是各自的数组。但这是隐藏地雷：
**以后只要给 `Card` 加任何可变状态**（升级、临时减费、附魔、标记「本回合已用」），
一方改动就会同时改到另一方。现在 `Card` 是只读的模板，所以安全 —— **别在这个块里给它加字段**。

> 这条**不是本块的活**，只登记，别顺手改 `setup()`（会动到 400+ 项测试）。
> 真正需要时单开一块：「`setup()` 里对每张卡 `Card.from_dict(原始模板)` 深拷贝」。

## §6 六条坑（每条都有人踩过）

1. **`attack_unit` 的返回值必须接。** 现在是 `attack_unit(u, ...)` 单独一行——
   这是整个缺陷的根。GDScript 不报「你没用返回值」，所以只有测试能抓。
2. **`board.has_unit_of("front")` 返回的是 owner 字符串**（空线返回 `"empty"`），
   不是数组、不是 bool。别拿它和 `true` 比。
3. **`position_of()` 对不在场上的单位返回空数组 `[]`**，`tmp[1]` 直接抛
   `Invalid access of index '1'`。`_is_guarded()` 的 `tmp.is_empty()` 守卫必须**在取下标之前**。
   （`_is_guarded(null)` 也要能活，顺手加 `target == null`。）
4. **别把 `_ai_attack_targets()` 写成「只给前线」或「只给支援线」**。
   空军能从支援线打支援线（M3.3 的 `_line_span_to`），所以候选要扫**全部三条线**。
5. **别用 `board.units_in()` 的遍历顺序当优先级**。`units_in` 是按格子下标从小到大，
   跟「谁该先被打」没关系。优先级只能靠 S2 那三条显式排。
6. **改完先 `--import` 再跑测试**。新增函数后不 import，`--script` 跑起来会拿旧缓存，
   症状是「改了没反应」。
