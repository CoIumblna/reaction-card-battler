# ADR-002：M1 不做战线，先只验证伤害管线

- 状态：已采纳
- 日期：2026-11-02
- 决策人：项目作者（在讨论 KARDS 路线后拍板）

## 背景

确定参考 **KARDS**（战场三线 + 费用曲线）而不是七圣召唤/杀戮尖塔后，面临一个选择：
M1 是直接上完整的棋盘（部署/战线/移动/行动花费），还是先把"卡牌 → 伤害 → 元素反应"这条管线做对？

约束：高二，每周 9 小时，M1 只有 6 周；作者第一次做完整项目。

## 决策

**M1 不做战线。** M1 的战场只有"玩家 vs 一个目标"，只验证：

- 出牌是否合法（能量、目标存活）
- 伤害公式与元素反应倍率
- 状态结算（护盾、治疗、buff 到期）
- 战斗日志与可测试性

**M2 再加入**：部署、战线（支援/前线）、移动、行动花费、Kredit 增长、召唤失调。

## 备选方案

| 方案 | 优点 | 缺点 |
|---|---|---|
| A. M1 直接上棋盘 | 一步到位，少一次重构 | 状态数量 ×3（位置/回合阶段/行动次数），6 周做不完，容易烂尾 |
| **B. 先做伤害管线（采纳）** | 范围小、可测试、能快速看到"出牌→伤害→反应"的闭环 | M2 要重写 `Battle` 的回合流程 |
| C. 先做 UI 再做规则 | 视觉反馈快 | 规则没定就做界面，界面会反复重做 |

## 理由

1. **可测试性优先**：`Damage.compute()` 是纯函数，能脱离战斗直接测；棋盘逻辑做不到。
2. **重构成本被控制住**：把伤害算法抽到独立文件 `src/core/damage.gd`，M2 变成"单位打单位"时**原样复用**，只需重写 `Battle` 的流程。
3. **风险前置**：第一次做项目，最大的风险不是"做小了"，是"做不完"。M1 结束时能跑通一局，是继续做下去的心理基础。
4. **符合 KARDS 的本质**：KARDS 的复杂度在"空间"，但它的**结算内核**仍然是"攻击力 vs 防御力 + 修正"。内核先对，空间后加。

## 代价

- M2 需要重写 `Battle` 的回合流程（预计 1–2 周）
- M1 的"敌人每回合打 4 点"是占位规则，M2 会被删掉
- M1 的玩法不够"好玩"（没有位置策略），需要有心理准备

## 影响

- `src/core/damage.gd` 独立成文件，M1/M2 共用
- `tests/` 拆成 `damage_test.gd`（纯算法）+ `battle_smoke_test.gd`（流程），M2 时前者不用改
- 数据结构预留：`Unit` 已有 `aura`（附着）与 `buffs`，M2 加"位置/是否已行动"即可
