## 1. 规则

> 目标身上**每 1 层 `defense_down`** → 它**受到的伤害 +1**。单位攻击和指令卡伤害都生效；到期就失效。

数据**已经在** `data/tables/statuses.json`，不用改：

```json
"defense_down": {
  "name": "减防",
  "effects": [ { "kind": "stat_mod", "stat": "defense", "value": -1.0, "timing": "passive" } ]
}
```

`value` 是 **-1.0**（防御 -1），而目标是「受到的伤害 +1」—— 中间差一个负号。

---

## 2. 写在哪里（两个位置的问题）

关键是搞清楚**三个东西各自能拿到什么**：

| 对象 | 手上有什么 | 拿不到什么 |
|---|---|---|
| `Buff`（`src/core/buff.gd`） | `kind` / `stacks` / `duration` 三个字段 | `stat`、`value` —— 它在 JSON 里 |
| `Unit` | `buffs` 数组 | `StatusTable`（不持有） |
| `Battle` | `status_table` 成员（`battle.gd:26`） | — |

所以「`value` 到底是多少」这件事，**只有 `Battle` 能顺手问到**，`Unit` 和 `Buff` 都问不到。

由此有两条路，任选：

- **路线 1（推荐）**：加值计算整个留在 `Battle` 里（它就是 `compute_damage` 的宿主，`status_table`
  是它的成员）。`unit.gd` 一行都不用动。
- **路线 2**：把「按属性查修正值」下放到 `Unit`，那 `Unit` 就必须**多收一个 `StatusTable` 参数**
  —— 因为它自己没有。签名大概长这样：`stat_mod(stat: String, table: StatusTable) -> int`。
  **注意是两个参数**，§36 旧版本写成 `stat_mod("defense")` 一个参数是错的，已订正。
  传参这件事本身没错，代价是 `Unit` 的每个调用点都得把 table 递进去。

两条路都能 7/7（我实测过），差别在「多一个参数」还是「逻辑留在一个文件里」。

## 3. 怎么判断「这条 buff 该不该算」（这里我上次写错了）

我上版给的写法是遍历 effects、同时筛 `kind=="stat_mod"` + `stat=="defense"` + `timing=="passive"`
三个条件。**你指出的问题成立**：这是个别扭的混合体 —— 它假装通用（在筛 `stat_mod` 这个 kind），
又把 `"defense"` 和 `"passive"` 写死。真正该问的是「我要不要做通用属性系统」，两个答案对应两种写法：

- **A. 只处理 `defense_down` 这一个状态**（当前阶段推荐）：直接认 `b.kind`，一眼看出意图。
  数值**仍然从 `status_table` 读**，不要写死 `1` —— 否则以后把 JSON 里 `-1.0` 改成 `-2.0`，
  代码不跟随，就是隐藏 bug。**认 kind、但不硬编码数值**，这是关键区分。
- **B. 做通用属性系统**：那就不要在 `compute_damage` 里挑 `defense`，而应该是一个
  `stat_mod(stat)` 通用查询，将来 `attack` / `hp` 修正都能用。但**现在没有第二个 stat 存在**
  （实测 `statuses.json` 四个状态里只有 `defense_down` 带 `stat_mod`），提前做通用层是空的。

**当前阶段选 A**：只有一个状态、一个属性，先做对再抽象。等 M3.6 / M3.4 出现第二个 stat_mod
状态时再抽 B，那时才知道要泛化到什么程度。

判据（你写的时候自查）：**改 JSON 里的 `value` 会怎样？** 代码行为应该跟着变。
如果不变，说明你把数值写死在代码里了，那是 bug。

## 4. 加在哪里

`Battle.compute_damage()` 现在只是把 `Damage.compute()` 的结果原样返回。它是**单位攻击**
（`attack_unit`）和**指令卡伤害**（`play_card`）两条路共用的出口 —— 所以改这一处，两处都生效。

两个约束：

1. **`immune` 时不要加**。`Damage.compute()` 返回的字典里有 `immune` 标记（元素免疫），
   此时伤害本来就是 0/无效，再加减防会算出「免疫还掉血」。
2. **别改 `Damage.compute()`，也别改 `damage.gd`**。它是 `static`（摸不到实例的 `status_table`），
   且 `combat_test` / `damage_test` / `status_test` 里有大量 `hit["damage"]` 断言，
   动它的返回字典形状会连带红一片。外层加算、让 `Damage.compute()` 保持纯函数最安全。

## 5. 四条坑

1. **叠层要用 `b.stacks`**。`unit.gd:92` 的 `add_buff()` 遇到同 `kind` 只做 `b.stacks += 1` 并刷新
   `duration`、**不新增 Buff 对象**。所以「叠 2 层」在数据上仍是 1 个 Buff。数 `buffs.size()`
   永远算 1 倍，`[3]` 红。
2. **加在目标侧，不是攻击侧**。是「目标受到的伤害 +1」，不是「攻击者攻击力 +1」。
   加错到攻击者身上，`[1]`（无 buff）也会跟着变。
3. **`Buff` 上没有 `stat` / `value`**。别指望 `b.value` —— 只有 `kind`/`stacks`/`duration`。
   数值必须经 `StatusTable.get_status(b.kind)` 问出来。
4. **别给 `Unit` 加 `status_table` 成员**（路线 2 的情况下）。用参数传。
   加成员会让单位脱离数据表就不能单测，`unit_test` 里那些直接 `Unit.from_dict(...)` 造的单位会崩。
