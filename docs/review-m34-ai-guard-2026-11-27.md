## §2 三处必须改（按严重度排序）

### 2.1 【致命】`battle.gd:161-162` 是死循环 —— 测试不是红，是**永远不返回**

你在这里写的是：**拿同一个攻击手、对着敌方 HQ 反复调用 `attack_unit`，没成功就 `continue` 再试一遍。**

`continue` 在 `while` 里的含义是「跳回条件重新判断」，而条件里的两个实参（攻击手、目标）自始至终没变过，
于是 `attack_unit` 每次都返回同一个 `false`，循环永远转下去。

实测症状（我这边跑过）：直接跑 `ai_guard_test`，**120 秒不退出，一个字符都不打印**；
`run_tests.bat` 也会卡在这个文件上（现在它会在 90 秒后杀掉进程并报 `[HUNG]`，见 §4 第 1 步），
看起来像「测试坏了」，实际是你的 AI 在转圈。

**为什么它不可能靠「再试一次」成功**：`attack_unit` 拒一次之后局面没有任何变化——被保护还是被保护、
够不到还是够不到、这个单位这一回合已经出手过还是出手过。**决定成败的是「打谁」，不是「试几次」。**
所以循环的变量必须是**目标**，不能是「同一个目标的重复尝试」。

**正确的形状，用一句话讲**：
`_ai_attack(attacker, owner) -> bool` 的职责是「向目标清单要一份按优先级排好的敌方目标列表，
从第一个开始依次交给 `attack_unit`，第一个被接受的立刻返回 true，全部被拒才返回 false」。
它内部**不含任何**「这个单位能不能打」的规则判断——射程、保护、行动花费、是否已出手，
全部由 `attack_unit` 一个函数说了算。它返回 bool 的唯一用途，是让调用方（`_ai`）知道「这个攻击手这回合还有没有事可做」。

顺带说清一件事：`attack_unit` 的返回值是**唯一的权威**——它内部会查 S3（`_is_guarded` 拒）、
查射程（`_line_span_to`）、查行动花费、查 `can_attack()`。**你在 AI 里不要再复述一遍这些规则**，
复述就等于同一套规则有两个副本，迟早分歧（`find_first_attackable` 就是那个已经被抛弃的副本）。

### 2.2 【根因】`battle.gd:163-169` 第二条分支**一行没改** —— [2] 红的正是它

这条 `elif` 里的逻辑仍然是老样子：**先问 `find_first_attackable` 要一个「敌方前线上的目标」，
拿到 `null` 就 `break` 跳出整条支援线的循环。**

`find_first_attackable()` 里写死了「跳过 Guard」，所以「敌方前线只有 Guard」时它返回 `null`，
`break` 一跳 → **这个支援线单位整个回合什么也没做**。这就是作业单 §0 那个「白扔回合」的 bug 本体，
它不在第一分支里，在这条 `elif` 里。

更深一层：**这个 `if/elif` 的结构本身就是错的**。它用「前线归谁」当总开关：

- 前线是己方的 → 只会「打 HQ」
- 前线是敌方的 → 只会「在敌方前线上找一个能打的」
- 前线为空 / 两边都有 → **两个分支都不进，一个都不打**

而真实约束是「**这个攻击手，能打到谁**」。同一条前线，近战能打、空军能越线、炮兵不吃反击——
这些差异在 `_line_span_to` 和 `attack_unit` 里，不在「前线归谁」里。
所以 S6 才要求目标清单扫**全部三条线**（`Board.LINES`），而不是「按前线归属分两条路」。

**改法方向**：把「先分两个分支、每个分支各写一遍选目标」换成「**遍历所有己方攻击手，每个都拿同一份清单去试**」。
分支越少，漏掉的情况越少。这正是路线 A 相对路线 B 的全部价值。

### 2.3 【实现】`_ai_attack_targets()` 有三个独立缺陷（`battle.gd:561-577`）

**(a) 返回了错的桶**

你把档 0/1/2 依次拼进了第一个桶（`battle.gd:575-576`），最后却返回**第二**个桶。
第二个桶只装「不受保护的非 Guard」，所以你现在**丢掉 HQ、也丢掉 Guard**。
要返回的是你辛苦拼好的那个桶。

**(b) HQ 会同时进档 0 和档 1 —— 两条并列 `if`，不是 `elif`**

你的外层是两个并列的 `if`：第一个判「是不是敌方 HQ」→ 进档 0；第二个判「是不是敌方单位」→ 再分 Guard / 非 Guard。
HQ 属于敌方、不是 Guard、通常也不被保护 → 它**又一次**被塞进「不受保护的非 Guard」那一档。
`u.is_hq` 这个排除项（作业单 §2.2 的排除表里写了）你没写。这两个判断必须二选一，不能都走。

**(c) 类型化数组 vs 从字典里掏出来的无类型数组 —— 这是会报 `SCRIPT ERROR` 的，`run_tests.bat` 直接判红**

你用了一个 `Dictionary` 装三个桶。从字典里取出来的值是**无类型 `Array`**，而函数声明返回 `Array[Unit]`。
实测（我在干净 worktree 用等价最小例子跑过）报的是 `SCRIPT ERROR: Trying to return a value of type "Array" from a function whose return type is "Array[int]"`，
而且紧跟在后面那行调试输出显示**返回的是空数组**——也就是说错误信息只是表象，**内容也一起丢了**。
结论很硬：**就算你把 (a) 改成返回第一个桶，只要桶是从字典里掏出来的，照样 SCRIPT ERROR。**

正解是别绕字典——直接声明两个**类型化**的数组变量（`Array[Unit]`），一个装「可直接出手的目标」，
一个装「Guard 候选」，遍历完后把第二个整体追加到第一个尾部。
类型化数组还有个额外的好处：往里 `append` 一个非 `Unit` 会当场报错，不用等到运行时才发现塞进了别的东西。

### 2.4 【空壳】`_ai_attack()` 还是直接返回 false，而且没人调用

`battle.gd:580-581` 原样没动，`_ai()` 里也**没有任何地方调用它**（`battle.gd:161` 绕过了它直接 `attack_unit`）。

实测指纹（Probe A）：把参考实现的 `_ai_attack` 改成直接返回 false，其他一概不动 →
`ai_guard_test` **14 项 / 6 失败**，和你的红基线**逐条相同**。结论：
**「只改 `_ai()` 不实现 `_ai_attack()`」等于什么都没改**，别指望它自己变绿。
